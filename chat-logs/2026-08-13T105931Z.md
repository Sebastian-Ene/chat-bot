Plan for indexing.

**`app/rag/ingest/index.py`**

- **Point IDs**: `uuid5(NAMESPACE_URL, f"{doc_id}:{chunk_index}")`. Deterministic, so re-ingesting overwrites in place rather than duplicating. Qdrant only accepts UUIDs or unsigned ints, which rules out the natural string key.
- **Payload**: `doc_id`, `doc_content_hash`, `chunk_index`, `text`, `headings`, `page_numbers`, `source_format`. Not `embed_text` — it's derivable, only exists to be vectorised, and storing it would put heading breadcrumbs one careless line away from the prompt.
- **Vectors**: `{"dense": [...], "sparse": SparseVector(indices, values)}` per point, from `sparse_indices_and_values()`.
- `index_document(client, chunks) -> int` — **one upsert per document, `wait=True`**. This is the invariant `state.py` reads back: a document is present at a hash or it isn't. Batching across documents would break it.
- `replace_document(client, doc_id, chunks)` — upsert the new points, *then* delete points for that `doc_id` whose `doc_content_hash` differs. That order matters: a crash between the two leaves duplicates, which are visible and repaired next run, rather than a gap where the document silently vanishes. It also covers a new version having *fewer* chunks, where deterministic IDs alone would leave a stale tail.
- `delete_documents(client, doc_ids) -> int` — delete by `doc_id` filter, for documents gone from disk.

**Runner restructuring** — this is the part worth your attention. Right now it's `parse_all` then (nothing). Indexing wants to be **per document**: parse → chunk → embed → upsert, one document at a time.

- Keeps memory flat: the current shape would hold 20 parsed documents plus 207 chunks plus 207 embeddings in memory at once. Fine at this size, wrong in principle.
- Makes the atomic-per-document invariant natural rather than something to be careful about.
- A failure at any stage costs one document, not the run.

The cost is that `parse_all` stops being the top-level call and becomes a per-document `parse`. I'd keep `parse_all` — the docling-marked tests use it — but the runner would no longer call it.

**Failure handling** — embed and index failures logged at ERROR and skipped per document, same contract as parse failures, feeding the same `failed` list and the non-zero exit.

**`RunReport`** gains `chunks_indexed` and `points_deleted`.

**Tests** (`tests/ingest/test_index.py`, in-memory Qdrant + stub embedder, no models):
- point IDs are stable across two runs and unique per chunk
- one upsert call per document, not per chunk
- payload round-trips, including empty `page_numbers` for HTML
- a changed document ends with only the new hash's points, including when it has fewer chunks
- a deleted document leaves nothing
- an empty chunk list writes nothing rather than an empty upsert
- plus a runner test that an unchanged document triggers no write at all

Then a real `docker compose run --rm ingest` over the 20 documents, and reading the collection back to confirm 207 points, one hash per document.

**Open question, your call**: should the payload store the full chunk `text`? It makes retrieval a single round trip and gives the generator its context directly — that's the normal RAG shape and what I'd default to. The alternative is storing only metadata and re-reading from disk, which keeps the index small but couples retrieval to the corpus volume being mounted in the api. I'd store the text.
