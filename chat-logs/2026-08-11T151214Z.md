# Plan: signed turns

## What this does and doesn't buy

**Closes:** a caller putting words in the assistant's mouth — the sharpest history-forgery vector, since the model treats its own prior turns as authoritative.

**Doesn't close:** a user writing hostile text in their *own* turn (that stays a guardrails problem), or truncating history. And because there's no auth, an attacker can always hold a genuine conversation and collect genuinely-signed turns — so this stops *fabricating* assistant output, not *obtaining* it.

So this is complementary to backend item 1, not a substitute. Guardrails on user turns are still needed either way.

## Recommended design: chained per-turn HMAC

Each turn gets a signature over the turn *and* everything before it:

```
sig_0 = HMAC(secret, conversation_id ‖ 0 ‖ role ‖ content)
sig_i = HMAC(secret, sig_(i-1) ‖ conversation_id ‖ i ‖ role ‖ content)
```

The server recomputes the chain across submitted history and rejects on mismatch. This catches edits, reordering, insertion and cross-conversation splicing in one check.

**Why chained rather than one signature per turn:** independent per-turn signatures let a caller reorder valid turns or splice a turn from another conversation. The chain fixes position and lineage.

**Why chained rather than a single whole-history token:** the client trims old turns to stay under the caps (10 turns / 10 000 chars). A single hash-of-everything token breaks the moment the client drops a turn. A chain lets the client drop a *prefix* and still verify the retained suffix, provided it also sends the signature at the cut point. Truncation stays possible — but truncation is context loss, not forgery.

`conversation_id` is minted at page render (alongside the existing chat token) so signed turns can't move between conversations. Signatures carry an expiry consistent with the existing TTL story.

## The crux: getting the signature to the client

The signature can only be computed once the full reply text exists, and the reply is streamed. Options:

| Option | Verdict |
|---|---|
| **Typed stream frames** (NDJSON/SSE: `{"type":"chunk"}` … `{"type":"done","signature":…}`) | **The only workable one.** Requires changing the wire format from `text/plain` and rewriting the frontend reader. |
| HTTP trailers | Rejected — effectively unusable from browser `fetch`. |
| Second "sign this text" request | Rejected — the client would supply the text, so we'd sign whatever we're handed. Defeats the purpose. |
| Server keeps the canonical text | Rejected — that's server-side session state, which §6.4 rules out by design. |

**This is the real cost of the feature:** `/api/chat` stops being a plain text stream. Anything reading it — the frontend, the API tests, future eval tooling — changes with it.

## Changes, file by file

1. **`app/signing.py`** *(new)* — `sign_turn(conversation_id, index, prev_sig, role, content)`, `verify_chain(conversation_id, turns)`; reuses `JWT_SECRET` or a dedicated `HISTORY_SIGNING_SECRET`.
2. **`app/routers/pages.py`** — mint and embed `conversation_id` next to the existing chat token.
3. **`app/routers/api.py`** — `Turn` gains `signature`; a validator verifies the chain before the request reaches the model; reject with 400 (a distinct code from the 401 token failure).
4. **Streaming response** — switch to NDJSON frames; emit a terminal frame carrying the new assistant turn's signature *and* the echoed user turn's signature.
5. **`app/static/chat.js`** — parse framed responses, store `{role, content, signature}`, send signatures back, keep the cut-point signature when trimming.
6. **Tests** — chain verifies; edited content rejected; reordered turns rejected; turn spliced from another `conversation_id` rejected; prefix-trim still verifies; unsigned/missing signature rejected; frontend round-trip through e2e.
7. **Docs** — `considerations.md` on the threat actually closed, and on truncation remaining open.

## Risks worth weighing before starting

- **Wire-format churn.** The streaming contract changes, and every consumer with it. This is the majority of the work, and it lands on code you've already stabilised.
- **Interaction with trimming.** Workable via the chain, but it's the fiddliest part and the easiest place to introduce a bug that silently rejects legitimate conversations.
- **Failure UX.** A verification failure means a user's page is stuck until reload. Needs its own message, like the 401 path.
- **Rotation.** Changing the secret invalidates every open conversation.

## My recommendation

**Do backend item 1 (guardrails) first, and treat signed turns as a follow-on** — guardrails are mandated by §6.3, cheap, and protect the user-turn vector that signing can't touch. Signed turns are a bigger, contract-changing change that protects one specific vector.

If the goal is demonstrating architectural reasoning for the interview, there's also a strong case for **documenting this design in `considerations.md` without building it** — the analysis is the interesting artefact, and the honest note that statelessness forces this trade-off may read better than the plumbing.

Good catch — that's a real bug today. A refusal streams back as a 200 with a body, so `chat.js` records it as a normal exchange: the attack message *and* the refusal enter history, and every later message is then judged against a conversation containing an attack. One refusal poisons the session permanently.

The client can't tell a refusal from an answer — both are 200 with text.

## Plan

**Signal the outcome in a response header, and have the client skip recording anything that isn't a real answer.**

1. **Move the analysis call into the `chat` endpoint**, ahead of the `StreamingResponse`. It has to happen before headers are sent, and headers are sent before the generator runs — so the current placement inside the generator makes the outcome unknowable at header time. Timings get created in the endpoint and passed into the generator so the stage breakdown is unchanged.
2. **`X-Chat-Outcome: answered | refused | unavailable`** on every response. Refusal and failure become plain 200 text responses (still 200, as you chose); the answer path stays a stream.
3. **`chat.js`** records the user turn and reply **only** when the outcome is `answered`. Refusals and failures still render in the bubble, they just never enter history.
4. **Tests** — header value per outcome; refused/unavailable still never reach retrieval or generation. Plus an e2e for the actual bug: send an attack, get refused, then send a legitimate message and confirm it's answered normally. That needs the fake to return `unsafe` based on message content, which I'll add.

## One decision

The alternative to a header is giving refusals their own status code (e.g. 403), which the client already branches on. I'd stay with **200 + header**: you chose 200 deliberately because a refusal is a content decision, not a protocol error, and a header keeps that while still being machine-readable.

Worth flagging: this also means a user who gets refused can simply carry on — their next question starts from a clean history, which is the behaviour you want, but it does mean an attacker gets unlimited retries with no accumulating penalty. Rate limiting would be the answer there, and there isn't any today.

Totals first (what cost is computed from), then per stage — so you can see which of the two calls is doing the spending, which matters given the analysis call is pure overhead on every request.

**How it's collected** — `TokenUsage` dataclass in `app/timings.py`; `analyse_query` and `stream_completion` each take an optional `on_usage` callback, so no signatures broke. Generation usage comes from `await stream.get_final_message()` once the stream is drained.

**Kept the DEBUG-only property** you asked for originally: `NoOpTimings.usage_recorder()` returns `None`, and the callers skip fetching usage entirely — so with performance logging off, `get_final_message()` is never called.

**`from_sdk` is tolerant of missing counters** — cost telemetry must never break a reply if a response omits a field.

Four things worth knowing for the cost write-up:

- **Refused and unavailable requests still log tokens.** You paid for the analysis call even when the verdict was "refuse" or the payload was unparseable — usage is recorded before parsing, so those rows are truthful. Refusals cost roughly one analysis call each, which is the number that makes the rate-limiting item concrete.
- **`cache_read` will be 0 throughout**, since the prompts are far below Haiku 4.5's 4096-token cache minimum. It's logged so the figure becomes meaningful once real chunks push the prefix past it.
- **A client disconnecting mid-stream loses the generation count** — `get_final_message()` never runs, so tokens spent won't appear. Rare, but it means totals are a slight undercount rather than exact.
- Numbers above are from the stub (120/30 per call); real figures need a live key.
