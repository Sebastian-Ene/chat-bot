## Document parsing

### Docling, unified across all three formats

Alternatives considered: best-of-breed per format (pdfplumber + python-docx +
BeautifulSoup), other unified parsers (Unstructured, Marker, MinerU), cloud
document-AI (LlamaParse, Azure Document Intelligence, Textract), and
LLM-as-parser (render pages to images, send to Claude vision).

- **Cloud document-AI — rejected.** Conflicts with the local/reproducible
  posture and adds another vendor and API key.
- **Per-format libraries — rejected.** Genuinely defensible: DOCX and HTML
  already carry table structure natively, so ML parsing buys nothing there, and
  PDF is the only hard format. But it means three parsers, three sets of edge
  cases and three things to explain, all behind a hand-written common
  interface. Also worth noting on licensing: PyMuPDF, the fastest PDF option,
  is AGPL — awkward for a submission. pdfplumber (MIT) would have been the
  pick.
- **Docling — chosen.** One library and one output model for all three formats.
  Critically, it emits a **structured document tree** (headings, paragraphs,
  tables, images, with page and section provenance) rather than a flat Markdown
  string — that provenance is what makes table-aware chunking and page-level
  citations possible. Layout analysis plus dedicated table-structure
  recognition covers the PDF case. MIT licensed.
- **Trade-off accepted:** ships ML models, so a bigger image and slower ingest.
  Ingest is offline, so it never touches the 5s completion target.

Docling's `HybridChunker` also turned out to settle most of the chunking
decision — see below.

### OCR — kept on

The corpus is digital-native, so OCR isn't needed for page text and switching it
off would be a free speedup. Kept on anyway because OCR reads text rendered
*inside* images — chart axis labels, legends, numbers baked into diagrams —
which the captioner does not reliably transcribe. The two complement each other
on exactly the figures that matter.

### Images — caption-first, generate only the gaps

Goal: every image ends up with an indexed, referenceable text description. Use
the caption the document already carries; only generate one when there isn't
one. The source of an existing description is **`PictureItem.captions`** — the
visible "Figure N: …" text Docling's layout analysis associates with the figure.
This works across all three formats and needs no extra code.

**Accessibility metadata is deliberately out of scope.** An earlier version of
this design was alt-text-first: prefer HTML `alt` / DOCX `descr` / PDF `/Alt`,
generate only when absent. Research into Docling killed it:

- Docling's HTML backend never reads the `alt` attribute (it handles `href`,
  `hidden`, `aria-hidden`, `style`, `id`, `class`, `start` — not `alt`), and its
  DOCX backend never reads `docPr`/`descr`.
- `PictureItem` has no field to hold such a value anyway. Its fields are
  `label`, `annotations`, `image`, `prov`, plus `captions` / `references` /
  `footnotes` inherited from `FloatingItem`. Only `captions` and VLM
  `annotations` carry text.

Getting alt text would therefore mean parsing each source file a second time
and joining to Docling's pictures on image content hash. Not worth the
complexity for a PoC, especially since real technical documentation usually
captions its figures visibly — which is the signal we actually want.

**A second Docling constraint shapes the design:** its built-in
picture-description enrichment appears to run for PDF only, not DOCX/PPTX
([docling#2225](https://github.com/docling-project/docling/issues/2225)) or
standalone images
([docling#2446](https://github.com/docling-project/docling/issues/2446)). So
caption *generation* is our own pipeline stage over the images Docling extracts,
rather than Docling's enrichment pipeline. Upside: the captioner model becomes a
free choice instead of one constrained by Docling's OpenAI-shaped API
integration.

- **Provenance:** record `extracted` vs `generated` per description. Cheap, and
  it lets the evaluation answer whether generated captions actually help
  retrieval or just add noise — the evidence that would justify upgrading the
  captioner.
- **Model:** start with Docling's default picture-description model. It is small
  and its captions are generic ("a bar chart") rather than factual ("return
  rates by product category, electronics highest at 12%"), and only the latter
  is retrievable. Accepted for now under the upgrade-on-evidence policy. The
  caption-first design also means it only runs on the minority of images that
  lack a visible caption.
- **Cache captions by image hash.** A few hundred images at CPU vision-model
  speeds is plausibly 30–60 minutes of ingest; re-running that every iteration
  would make development miserable, and hash-keyed caching fits the incremental
  ingestion design anyway.

**1. HTML yields no image bytes.** Docling finds the `PictureItem` but carries no pixels for it. ## Where Docling is actually needed

**Only in ingestion.** Two touch points, both ingest-side:

- `docling` (the heavy one: torch, transformers, layout + table models, OCR) → parsing
- `docling-core` (`HybridChunker`, the document types) → chunking, which also runs at ingest time

At request time the API does: query analysis (Anthropic), **query embedding**, Qdrant search, generation (Anthropic). Docling appears nowhere. So it can be removed from the API image entirely.

## The catch that decides how much the split is worth

The API still needs **BGE-M3 to embed the incoming query** — and that pulls torch (~1 GB) plus weights (~2 GB). So splitting off Docling saves the parsing models, OCR engine and any captioner (~1–2 GB), but does **not** on its own give you a light API container.

To actually get a small API image you'd also have to change how the query is embedded — ONNX runtime (FastEmbed) instead of torch. Two risks there: BGE-M3's **sparse** vectors may not be available in FastEmbed, and index-time and query-time embeddings must come from the same model or the vectors don't line up. Numerically they'd be near-identical, but it's a real thing to verify rather than assume.

## Options

**A. One image, one container.** Current plan. Simplest; ~6–8 GB; ingestion competes with request handling for CPU.

**B. One image, two entrypoints** (`api` and `ingest` commands, same build). Splits *processes* without splitting builds. Gets you CPU isolation and a clean ingest lifecycle for almost no work — the image stays fat, but it's built once.

**C. Two images: API + ingester (+ Qdrant).** True split. Ingester owns docling, chunking and index-time embedding; API owns query embedding, search, generation. Saves the parsing stack from the API image, costs a second Dockerfile and a trigger mechanism.

**D. C plus an ONNX query embedder.** The only version where the API image gets genuinely small (~hundreds of MB). Buys the most, risks the sparse-vector support and the index/query symmetry above.

## What I'd recommend

**C**, and treat **D** as a follow-on once the embedder is real and you can verify sparse-vector parity.

The strongest argument isn't image size — it's **concurrency**. The brief mandates concurrent access and a 5 s completion target, and ingestion is minutes of pinned CPU. In a single container, one ingestion run degrades every in-flight chat request. That's the `work.md` thread-pool-and-semaphore item, which becomes largely unnecessary if the two workloads simply don't share a container. That's a much better answer to a concurrency requirement than a semaphore.

**On the ingest endpoint:** keep it on the **ingester**, bound to the compose network only, never published to the host. The API's `POST /api/ingest` becomes a thin proxy carrying the shared internal key. The endpoint still takes no path — `CORPUS_DIR` is a setting on the ingester — and the corpus directory is a volume both containers can see (the API only to serve/inspect, the ingester to read).

Two consequences worth naming: this **revises requirements §5**, which currently specifies two containers and no load balancer; and it means the ingester holds the only copy of the index-time embedder, so a model change has to be rolled out to both sides together.

## The argument against is the same one that justified the first split

Right now: the ingester embeds chunks on its own CPU, the api embeds queries on its own CPU. **No contention.**

With a shared embedder service, a big ingestion run floods it with thousands of chunks, and query embedding queues behind that work. Chat latency spikes during ingestion — exactly the interference we split Docling out to eliminate, reintroduced one layer down.

You could fix it with separate replicas for api and ingester traffic, but then you're running two model instances again (so no memory saving), at four or five containers, for a PoC.

Secondary costs: query embedding sits on the 5 s critical path, so it gains a network hop; and the api gains a hard availability dependency plus startup-ordering requirements.

## What genuinely argued for it

One thing, and it's real: **a single source of truth for the model**, which structurally removes the coordinated-rollout risk I flagged — index-time and query-time embeddings drifting apart degrades retrieval *silently* rather than failing loudly. That's the worst kind of bug.

## Cheaper fix for that exact risk

Make the mismatch **fail loudly** instead of preventing it architecturally:

- The ingester records the embedder identity — model name, revision, vector dimension, and whether sparse is enabled — into the Qdrant collection metadata when it creates or writes the collection.
- The api reads that at startup and refuses to serve if its own embedder doesn't match.

That's roughly twenty lines, no new container, no new failure mode, and it converts a silent-degradation bug into a boot-time error with a clear message. It also gives you a natural place to record the model version for the write-up.

## Where a split *would* pay

If the embedder moved to a GPU, or if you needed to scale embedding independently of the API — neither applies here, and both are fair to name as "what would change this decision" in the write-up.

## Correcting myself first

I said the split gives "no contention." That's **wrong on a single host**. Docker containers share the host CPU by default — separate containers do *not* mean separate cores. Without explicit limits, a Docling run in the ingester will still starve the api.

What the split actually buys is **process isolation**: separate event loops, separate memory, separate failure domains. An ingestion run can't block the api's event loop or OOM it. Real CPU isolation needs `cpus:` / reservations in compose, which should be an explicit task rather than an assumption.

## But the embedder is a different problem from Docling

The distinction isn't "CPU-bound or not" — it's **required by the request, or competing with it**:

- **Ingestion** is background work that *competes* with requests. Removing it from the request path is a genuine win.
- **Query embedding** *is* the request. Every chat turn must embed its query before it can search. Move it to another container and the request still waits the same ~30–100 ms, plus a network hop. You relocate the cost; you don't remove it.

So splitting the embedder makes the critical path slower, not faster.

## What actually fixes the embedder blocking

Two things, both independent of container topology:

1. **Get it off the event loop** — a sync CPU call inside an async handler stalls *every* concurrent request, not just its own. That's the `work.md` task, and it's the real fix. A thread pool with a bounded semaphore means concurrency degrades predictably instead of thrashing.
2. **CPU limits in compose** — cap the ingester and reserve headroom for the api, so a background run can't crowd out request work on a shared host.

Worth being clear about the ceiling here: on one machine with N cores, concurrent query embedding is genuinely rate-limited by CPU. A semaphore makes that queue orderly and the latency predictable; it doesn't create capacity. If the 5 s target ever fails under concurrency, the honest answers are fewer/cheaper embedding calls, a smaller model, or more cores — not a different container layout.

Shall I add the CPU-limits task and correct the "no contention" claim in `considerations.md` to say process isolation rather than CPU isolation?
