## Module

**`app/rag/ingest/parse.py`**

- **One `DocumentConverter`, built once and reused** — it loads layout, table and OCR models, so per-document construction would dominate the run. Cached at module level.
- PDF options: `do_ocr=True`, `do_table_structure=True`, and **`generate_picture_images=True`** — without that last one Docling discards figure images and the whole caption stage has nothing to work with. That's from the spike, not the docs.
- `parse(document: DiscoveredDocument) -> ParsedDocument` wrapping the `DoclingDocument` with `doc_id`, `source_format`, `page_count`, `table_count`, `picture_count`, and parse duration.
- INFO log per document (pages/tables/pictures/seconds), since parsing is the slow part of a run and this is where you'll look when it drags.

## Three decisions

**1. What happens when one document fails to convert?**
I'd **log the error, skip it, continue**. Rationale: with state derived from Qdrant, a skipped document simply stays un-indexed and is retried automatically on the next run — no bookkeeping needed. Aborting the run would let one malformed file block the other 24. The run summary reports failures so they can't pass unnoticed.

**2. The `lang` payload field.** Nothing gives it to us for free — Docling doesn't detect language, and inferring from our `-de`/`-en` filenames would be a corpus-specific trick that wouldn't survive real documents. Options: defer it, or add a detector dependency (`lingua`/`langdetect`). I'd **defer** — BGE-M3 is multilingual so retrieval doesn't need it, and it's currently only useful for filtering and analytics we don't have. Worth recording as a known gap rather than faking it.

**3. Test strategy.** Parsing needs real models, so those tests are slow (tens of seconds, minutes on the 25-page reference). I'd add a **`docling` marker**, exclude it from the default run alongside `e2e`, and keep it to three files — a PDF, a DOCX and the HTML — asserting the spike's findings still hold: images present for PDF/DOCX, absent for HTML; tables found in the unruled German document. Fast unit tests cover the converter's configuration and the failure path with a stubbed converter.

Note this changes `addopts` to `-m 'not e2e and not docling'`.

**Option 3 — baking the models at build time.** That's the production pattern, and by a wide margin.

Why: a production image should be immutable and self-sufficient. Baking means no network call on first request, no writable directory inside the runtime filesystem, no dependency on a model host being reachable (or on a model URL still resolving the same bytes next year), and identical behaviour on every replica. When 20 pods start at once, options 1 and 2 have all 20 racing to download into their own storage; option 3 has them start immediately. Option 2 is the one I'd rank *last* for production, even though it's the one you see most often in the wild.

The problem isn't the download — it's what `chown` buys the attacker. Making a directory inside site-packages writable by the runtime user means the process can modify code that Python imports. Anyone who gets execution in that container can drop a `.pth` file or overwrite a module and have it persist and re-execute on the next import — a straightforward persistence primitive. Read-only application code is one of the cheaper container hardening wins, and this trades it away for a cache directory. Plenty of production images do exactly this; it still tends to be a finding in a security review.

The operational cost is real too: the writable layer is per-container and disappears on recreate, so every deploy, restart, and scale-up re-downloads the models over the network. Option 1 at least keeps them in a volume that survives.

So the ordering for prod is 3, then 1, then 2. Option 2's only genuine advantage is that it's one line and needs no build-time network — which is why it shows up in so many Dockerfiles.

If you want to keep it a one-liner without the writable-code problem, there's a variant worth mentioning: point `HOME` at a writable directory and symlink from there, or `chown` a directory *outside* site-packages and symlink into it — that's essentially option 1 minus the volume, and it keeps application code read-only.

- **Scheduled ingestion is a batch job, not a request.** In production this is more likely a cron/k8s Job than an HTTP call — an entrypoint that exits with a status code fits that shape, and a long parse run doesn't fight request timeouts.
- **The demo.** Copying `docs-later` in and running one command is easier to show than curling an internal service that isn't published to the host.

**2. Chunking (`app/rag/ingest/chunk.py`)**
- `HybridChunker` with BGE-M3's tokenizer, `max_tokens` 512.
- `contextualize()` for the embedded text, so the heading path travels with the chunk; the raw text is kept separately for display and citation.
- A `Chunk` dataclass: `doc_id`, `doc_content_hash`, `chunk_index`, `text`, `embed_text`, `headings`, `page_numbers`, `source_format`.
- Page provenance only exists for PDF — DOCX/HTML chunks carry an empty list, which the citation format has to tolerate.

**3. Collection (`app/vector_store.py`, extended)**
- `ensure_collection()` — idempotent create with size 1024, cosine. Called by the job, not by the api; the api only reads.
- Payload index on `doc_id`, since every delete and every state read filters on it.

**4. Indexing (`app/rag/ingest/index.py`)**
- Deterministic point IDs: UUIDv5 over `f"{doc_id}:{chunk_index}"`, so re-ingesting overwrites rather than duplicating.
- **One upsert per document**, `wait=True` — the invariant `state.py` depends on. A document is indexed at a hash or it isn't.
- Changed document: upsert the new points, then delete points matching `doc_id` with a different `doc_content_hash`. That order means a crash between the two leaves duplicates (visible, and repaired next run) rather than a gap.
- Deleted documents: delete by `doc_id` filter.
