There is a genuine one-call option: **denormalise at index time**, storing each chunk's neighbour text in its own payload. **3. Native citations — why formatting matters.**

Anthropic's citations aren't something the model is asked for in a prompt; they're a structured feature. You pass retrieved context as `document` content blocks with `citations: {enabled: true}`, and Claude returns text blocks carrying a `citations` array — each entry naming which document it drew from, the cited span, and the exact `cited_text`. The provenance is machine-readable, not a `[1]` the model wrote and might invent.

The relevant part for us is `document_index`: each citation points at a document *by position in the list you sent*. So:

- **Chunks as separate document blocks** → citation 0 means "that chunk", and I can map it back to `doc_id`, page and headings for display. Attribution is per-chunk and verifiable.
- **Chunks flattened into one numbered string** → one document block, every citation points at index 0, and the `[3]` in the text is just something the model typed. Exactly the hand-rolled citation the requirement avoids.

- **Custom-content documents** let a document hold a list of text blocks, and citations then resolve to a *block index* rather than character offsets. - **Citations stream.** They arrive as deltas alongside the text, so the frontend can render them as the answer appears rather than waiting for the end.

## Side by side

| | **1 — embedding in the api image** | **2 — separate embedder service** |
|---|---|---|
| **api image** | ~7 GB (torch + transformers + BGE-M3 weights) | stays 507 MB |
| **ingest image** | 18.3 GB unchanged | ~11 GB — FlagEmbedding and the weights move out |
| **new image** | none | embedder ~7 GB |
| **total disk** | ~25 GB, BGE-M3 and torch stored twice | ~18.5 GB, model stored once |
| **RAM per api replica** | +~2.5 GB — every replica loads its own copy | unchanged (~50 MB); one embedder holds the model |
| **query latency** | 33 ms, in-process | ~35–40 ms (+1–3 ms compose hop, ~8 KB per vector) |
| **api startup** | +10–20 s loading weights | unchanged |
| **api rebuild** | ~8–10 min | seconds |
| **new failure mode** | none | embedder down → retrieval returns nothing (already handled: degrades to "cannot answer") |
| **drift risk** | two processes, same code and settings | *stronger* — literally one process embeds both corpus and queries |
| **scaling** | api replicas can't scale without multiplying model memory | embedder scales independently; could take a GPU node |
| **new code** | none | Dockerfile, service, HTTP client, contract tests, compose wiring |
| **effort** | ~30 min | ~2–3 h |

**The case for 1:** nothing new to build, no network in the retrieval path, and the tests already stub `embed_documents` so nothing changes. For a single-user PoC on one machine, the 7 GB image costs disk and build time and nothing else.

**The case for 2:** it's the shape production actually takes — model serving separated from the app so they scale on different axes, which matters because embedding is CPU-heavy and the api is IO-bound. It also *reduces* total disk by ~6 GB by storing BGE-M3 once, keeps the api's fast rebuild loop, and gives the strongest possible answer to "how do you guarantee index-time and query-time embeddings match?" — same process, not just same config. The cost is a third service and roughly a morning.

The honest tiebreaker: latency and correctness are near-identical, so this is a complexity-versus-architecture call, and your brief is graded on architectural reasoning rather than feature count.

# Query embedding in the api image

## Context

`app/rag/retriever.py` now embeds the query before searching Qdrant, so the api
imports `app.embedding` → `FlagEmbedding`. That package lives in the `ingest`
dependency group, and the api image installs main dependencies only

```
api-1 | ModuleNotFoundError: No module named 'FlagEmbedding'
```

The stack is currently broken — `docker compose up` brings up an api that cannot
serve a request. This is the cost that choosing BGE-M3 for dense+sparse always
implied: query-time and index-time embedding must use the same model, so the
model has to exist wherever queries are embedded.

Chosen: bake it into the api image. In-process embedding at 33 ms, no new
service, no network hop in the retrieval path. The api image grows from 507 MB
to roughly 7 GB and gains ~2.5 GB RSS per replica; on a single-machine PoC that
costs disk and build time and nothing else. The separate-embedder-service shape
is the better production answer (one model copy, independent scaling) and is
worth mentioning in the docs, but it is a third service and a morning of work
for no behavioural gain here.

Docling stays out of the api. That boundary is still real: parsing is the 18 GB
half, and no request path touches it.
