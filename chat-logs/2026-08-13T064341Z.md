Plan for embedding. One decision needs your call, at the end.

**`app/embedding.py`** — shared by the ingest job and (later) the api, so query-time and index-time use one implementation:
- `get_embedder()` cached per process; loads BGE-M3 once and logs the load time.
- `embed_documents(texts) -> list[Embedding]` and `embed_query(text) -> Embedding`, where `Embedding` holds `dense: list[float]` (1024-d, normalised) and `sparse: dict[int, float]` (token id → weight).
- Two entry points even though BGE-M3 needs no asymmetric prefix — because the api will call the query side, and a single shared function invites someone to batch a query through the document path with different settings.
- Batched, batch size a setting; the container's memory is the constraint, not throughput.
- No `async`: it's CPU-bound. The api will hand it to a worker thread (already on the task list); the job doesn't care.

**Sparse handling** — Qdrant wants `indices`/`values` arrays, so the dict converts at index time. Sparse weights come from the same forward pass as dense, so hybrid costs one model, not two.

**Baking** — the warmup step gains an embed call, so the weights land in the image like the OCR and tokenizer models. BGE-M3 is ~2.3 GB, which takes the ingester image from ~9.5 GB to ~12 GB. Worth flagging now rather than at build time.

**Tests**
- Fast (`tests/test_embedding.py`): stubbed model — batching splits correctly, sparse dict converts to Qdrant's index/value form, empty input returns empty, query and document paths hit the same loaded model.
- Real (marked, kept out of the default run): dense is 1024-d and unit-norm, sparse is non-empty and keyed by real token ids, the same text embeds identically twice, and a German query is closer to its German chunk than to an unrelated one — the one assertion that actually proves the model works for this corpus.

**The decision — which library:**

1. **`FlagEmbedding`** (BAAI's own). The only one that returns BGE-M3's *learned* sparse weights, which is what "dense + sparse from one model" normally means. Pulls torch — already unavoidable for dense.
2. **`fastembed`** (Qdrant's). ONNX, no torch, much lighter for the api image later, and integrates cleanly with the client. Its usual sparse partner is **BM25**, which is statistical rather than learned — so "hybrid" would mean BGE-M3 dense + BM25 lexical, not BGE-M3's own sparse. Arguably fine, and BM25 is strong on exact terms like `F250`.
3. **`sentence-transformers`** — dense only; sparse would need a second model. Rules itself out given your call.

I'd go with **1** for the ingest job, since you asked for dense + sparse and FlagEmbedding is the honest reading of that. The cost lands later: the api needs the same embedder for queries, and that means torch in the api image too — the thing we worked to keep out. Option 2 avoids that at the price of the sparse side being BM25 rather than BGE-M3's.

Which one?
