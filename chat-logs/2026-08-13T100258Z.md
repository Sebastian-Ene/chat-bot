## user — 12:41

pros vs cons for cosine vs dot

## assistant — 12:41

Given BGE-M3 returns unit-norm vectors, the two are mathematically identical here — cos(a,b) = a·b when ‖a‖=‖b‖=1. So this is entirely about what happens when that assumption breaks.

**Cosine**
- Correct whatever the vectors' magnitudes are. If `normalize_embeddings` ever gets flipped off, a model gets swapped for one that doesn't normalise, or someone hand-inserts a vector, ranking stays right.
- Not actually slower at query time: Qdrant normalises vectors *once at upsert* and then uses dot product internally. You pay a one-off cost per point, not per search.
- Downside: it masks the mistake. Unnormalised vectors would go unnoticed because results stay sensible — you lose the signal that something upstream changed.

**Dot**
- Marginally cheaper on insert (no normalisation pass). At 207 chunks this is unmeasurable; at hundreds of millions it's a real ingest saving.
- Honest about magnitude: if you ever *wanted* magnitude to carry meaning — say boosting authoritative documents by scaling their vectors — dot is the only option that respects it.
- Downside, and it's the serious one: if vectors stop being normalised, dot is silently wrong. Long chunks get larger norms, so they rank higher regardless of relevance. No error, no log line, just gradually worse answers — exactly the failure mode this project keeps trying to design out.

One detail worth knowing: the **sparse** vector uses dot product regardless. Qdrant's sparse index has no distance parameter, so this choice only concerns the dense branch.

My recommendation stays cosine. The cost is a one-off normalisation we're already paying for anyway, and the benefit is that a change to the embedding config degrades into "still correct" rather than "subtly wrong." Precision here is worth more than insert throughput on a corpus this size.

If you'd rather have dot, the sensible pairing is a test asserting the vectors are unit-norm at index time, so the assumption is enforced rather than trusted — we already have that assertion in the embedding tests, so it's a defensible choice too.

## user — 12:43

should we normalize_embeddings in the first place? pros vs cons

## assistant — 12:44

Yes, and the reason is stronger than the cosine/dot question.

**For normalising**
- **It matches how BGE-M3 was trained.** The model was trained contrastively with cosine similarity — the objective operates on normalised vectors. Using raw magnitudes means scoring in a geometry the model never optimised for.
- **Scores become comparable across queries.** A normalised similarity lives in [-1, 1] and means roughly the same thing for every query, so a threshold like "below 0.5, treat as no match" is meaningful. That matters concretely here: the grounding requirement needs a "no relevant context → say I don't know" path, and that needs a threshold you can actually pick. With unnormalised scores, the cutoff drifts per query and there's nothing stable to tune.
- **Magnitude in transformer embeddings is mostly an artefact.** It tracks token count and frequency effects rather than relevance — long chunks get bigger norms. Keeping it means length quietly influences ranking.

**Against**
- You lose magnitude entirely, which in principle could carry signal — some retrieval setups use it as a confidence proxy, or scale vectors deliberately to boost authoritative documents. But BGE-M3 isn't trained for either, so the signal you'd be preserving is noise plus length bias.
- Very marginal compute at encode time. Irrelevant at any scale we'll see.

So: keep `normalize_embeddings=True`. That's the setting that makes the threshold-based refusal path possible later, and it's what the model expects.

Which does fold back into the previous question — with normalisation on and asserted by a test, cosine and dot are equivalent, and the choice between them is just which failure you'd rather have if that assertion ever stops being true. I'd still take cosine.

Shall I proceed with the collection plan as described (cosine, normalisation on)?
