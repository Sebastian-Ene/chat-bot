1. **The image grows.** This project's rule is models baked in, never downloaded at runtime — so the ingest image goes from 18.3 GB to roughly 19 GB (SmolVLM) or 24 GB (Granite). `C:` currently has **20 GB free**, having hit zero earlier today. Granite doesn't fit; SmolVLM does, barely.
2. **A rebuild is needed either way** — the warmup `RUN` would have to pull and bake the new weights, so this isn't a config flip.
3. **Docling has a third path I hadn't accounted for:** `PictureDescriptionApiOptions` — describing figures via a remote API endpoint, with `url`, `headers`, `prompt`, `concurrency`. That means a hosted vision model can plug into Docling's own pipeline rather than needing bespoke code alongside it. Whether it speaks Anthropic's message shape or only OpenAI-compatible needs checking, but structurally the option exists.

So the local-VLM option is meaningfully more expensive than "flip a flag", and its likely outcome is still a generic caption that doesn't answer `qa-005`.

## Important OpenAI compatibility limitations

### API behavior

Here are the most substantial differences from using OpenAI:

* The `strict` parameter for function calling is ignored, which means the tool use JSON is not guaranteed to follow the supplied schema. For guaranteed schema conformance, use the native [Claude API with Structured Outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs).
* Audio input is not supported; it will be ignored and stripped from input
* Prompt caching is not supported, but it is supported in the [Anthropic SDKs](https://platform.claude.com/docs/en/cli-sdks-libraries/overview)
* System/developer messages are hoisted and concatenated to the beginning of the conversation, as Anthropic only supports a single initial system message.

Most unsupported fields are silently ignored rather than producing errors. These are all documented in the following sections.

### Output quality considerations

If you’ve done lots of tweaking to your prompt, it’s likely to be well-tuned to OpenAI specifically. Consider reworking it for Claude using the [prompting best practices guide](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices).

### System / developer message hoisting

Most of the inputs to the OpenAI SDK clearly map directly to Anthropic’s API parameters, but one distinct difference is the handling of system / developer prompts. These two prompts can be put throughout a chat conversation via OpenAI. Since Anthropic only supports an initial system message, the API takes all system/developer messages and concatenates them together with a single newline (`\n`) in between them. This full string is then supplied as a single system message at the start of the messages.

### Thinking support

You can enable [thinking](https://platform.claude.com/docs/en/build-with-claude/thinking) by adding the `thinking` parameter. On current models thinking is adaptive, with Claude deciding when and how deeply to think, and on Claude 5 models it is on by default; manually configured extended thinking is a legacy mode. While thinking improves Claude's reasoning for complex tasks, the OpenAI SDK doesn't return Claude's detailed thought process. For full thinking features, including access to Claude's step-by-step reasoning output, use the native Claude API.

entirely at chunking.

`docs/work.md` deferred this "until the `image_only` questions are shown to

The two failures need different things:

| | `qa-005` | `qa-007` |
|---|---|---|
| wants | −10 °C series at month 15 = 40 % | Friday ≈ 505 |
| format | PDF | **HTML** |
| in the image as | a plotted point — never text | a printed bar label |
| why it fails today | OCR runs, but there is no text to read | figure never reaches the pipeline at all |

So a generic caption ("a line chart of battery retention") answers neither. The
description has to **transcribe chart data**, and it has to reach HTML figures
too.

## Approach

Describe every figure with Claude vision through Docling's own API describer,
cache by image hash, and write the result where the chunker already reads it.

**Why not Docling's local VLM:** `smolvlm`/`granite` weights are not installed
(HF cache holds only BGE-M3 and the layout/table models), so it means +0.5–6 GB
baked into an 18.3 GB image with 20 GB free on `C:` — and a generic caption
still would not answer `qa-005`.

### 1. Describe via Docling's API path, driven by us

Docling's built-in enrichment is **PDF-only**, so it cannot fix `qa-007`.
Instead reuse Docling's transport directly for all three formats:

- Build a `PictureDescriptionApiOptions` (`docling.datamodel.pipeline_options`)
  pointed at `https://api.anthropic.com/v1/chat/completions`, with
  `headers={"Authorization": f"Bearer {key}"}` and
  `params={"model": ..., "max_tokens": ...}`.
- Call `docling.utils.api_image_request.api_image_request(...)` per figure. It
  builds the OpenAI-shaped body Anthropic's compatibility layer accepts
  (`content[].image_url.url` as a base64 data URI) and parses
  `choices[0].message.content`, with retry/backoff already built in.

This keeps Docling's request plumbing while letting us feed it images from every
format, which the built-in enrichment cannot.

> Anthropic documents the compatibility layer as "not a long-term or
> production-ready solution". Acceptable for a PoC and worth a line in
> `docs/considerations.md`; the native-SDK alternative is a ~60-line custom
> describer if that caveat ever bites.

### 2. Get the image bytes — the HTML gap

- **PDF / DOCX** — `PictureItem.image` is populated (spike 1 confirmed).
- **HTML** — it is **not**. Resolve the figure from the document instead: the
  images sit beside the HTML on disk (`corpus/docs-initial/coverage/images/
  support-volume.png`), so map each `PictureItem` to its `<img src>` in
  document order and load the file relative to the document's directory.

New module `ingestion/describe.py`, called from `ingestion/runner.py` between
`parse()` and `chunk()`.

### 3. Prompt for data, not a caption

Model is **`claude-haiku-4-5`** — the same one the app uses everywhere, kept as
its own `describe_model` setting so it can be raised without touching
`anthropic_model`.

Roughly: *"Describe this figure so its content is findable by search. If it is a
chart, list each series and its value at every labelled position. Use the
document's language."* The `qa-005` answer only exists if the description
carries `15 → 40 %` for the −10 °C series.

Haiku is the weakest of the vision-capable models at reading an unlabelled
plotted point, so **this is the step most likely to need a second pass**. Order
of attack if `qa-005` still fails: sharpen the prompt first (ask for a value at
every x-tick, and to state the axis scale it inferred), then raise
`describe_model`. `qa-007`'s value is a printed bar label, so it should come out
regardless.

### 4. Cache by image hash

SHA-256 of the image bytes → description, in a JSON file under a new
`IngestSettings.description_cache` path. Checked before every call, so
re-ingestion and `--force` cost nothing. Needs a writable path in the container
(the corpus mount is read-only) — bind-mount alongside `./logs`.

### 5. Write it where the chunker reads it

`PictureItem.meta` via `PictureMeta(description=DescriptionMetaField(...))`,
falling back to the deprecated `annotations` — spike 2 proved this reaches
`contextualize()` and therefore both `text` and `embed_text`.

### 6. Failure is per-figure, never per-document

No key, API error, or unreadable image → log WARNING naming the doc and figure,
index the document without that figure, exit 0. Same degradation as a failed
OCR; nothing regresses relative to today.

## Consequence to accept

**The ingest job regains an `ANTHROPIC_API_KEY`.** `IngestSettings` currently
needs no secrets and neither Dockerfile carries placeholder credentials — that
was deliberate, and this reverses it. The key becomes optional-but-recommended:
absent, ingestion still runs and figures stay undescribed (§6).

**How it works** — the app already measures every stage and writes `logs/api/performance.log`; re-deriving them client-side would only reproduce the total. The harness now captures `X-Request-ID` from each response and joins on the `[a3c790e8]` prefix in the log. That gives real per-stage numbers rather than an approximation, at zero extra cost. The same table goes into the Markdown report.

Three deliberate choices:

- **Answered requests only.** A refusal never reaches retrieval or generation, so including refusals would drag every median down and misrepresent the pipeline.
- **Degrades to nothing.** The log is DEBUG-only, and a `--base-url` pointing at a remote api has no local log — in either case the section is simply absent. `--performance-log` overrides the path.
- **p95 as well as median and max**, since the earlier runs showed the tail is where the 5s budget is at risk, not the median.

Two caveats worth stating:

**I found a bug in my own code while testing** — `r["request_id"]` raised `KeyError` on report files written before this change. Now uses `.get()`, so an old file skips the section instead of crashing the run.

**The numbers above are synthetic.** The saved results predate the `request_id` field, so I paired the last 26 real log entries with the stored answers to exercise the reporting path. The *timings* are real (from your actual log), but the join is fabricated. A genuine join needs one fresh eval run — ~96 Haiku calls — which I haven't started.
