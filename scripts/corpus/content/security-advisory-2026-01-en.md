# Summary

A device pairing token generated by the hub remained valid after pairing
completed, and was accepted again for up to 24 hours. An attacker already on the
same local network could use a captured token to pair an unauthorised device to
the hub. The issue is fixed in firmware 4.3.

# Severity

Rated moderate. Exploitation requires prior access to the local network and the
ability to observe the pairing exchange, and yields the ability to add a device
rather than to read existing data or control heating directly.

| Affected firmware | Status | Action |
| --- | --- | --- |
| 4.3 and later | not affected | none |
| 4.2.x | affected | update to 4.3 |
| 4.1.x | affected | update to 4.3 |
| 4.0.x | affected | update to 4.3 |
| 3.9 and earlier | affected, unsupported | replace or update; 3.x is out of support |

# What was changed

Pairing tokens are now single-use and expire 90 seconds after they are issued,
matching the pairing timeout. The hub additionally rejects a pairing attempt from
a device identifier that is already present in its table.

# What you should do

Hubs update themselves overnight; no action is required beyond letting the update
apply. Confirm the running version in the app under Settings. If a maintenance
window is configured, the update applies inside that window, which can delay it
by up to a day.

Review the device list after updating. A device you do not recognise should be
removed and the incident reported through support.

# Detection

Unauthorised pairing appears in the hub event log as a pairing event outside the
window in which you were pairing something. The log retains 90 days.

# Credit

Reported through the coordinated disclosure process. No exploitation in the field
has been observed.
